BiteExpress · restaurant discovery
recommendation

Take the peak restaurant list off the Gurugram monolith this year.

Keep SQL as the source of record until Atlas can own restaurants by country. I will not move orders or payments to fix a slow list.

Two clocks: reliability at lunch in 6–12 months, then cloud, countries, and data rules in 2–3 years.

today

What is hitting BiteExpress

  • peak At lunch and dinner the restaurant list on the Gurugram monolith is slow. People leave before they pick a place.
  • revenue If the list fails, checkout never starts. Payments never see that order. We lose money on a read, not on a charge.
  • blast Consumer apps, the partner portal, riders, and dashboards share one backend. A hot list slows everything else.
  • gap Some SQL copies already exist, and payments are already outside. Discovery is still inside, so copies do not save the lunch list.

why this, why mongo

Why discovery, and why MongoDB

  • first Discovery is the hottest read. If it is slow the order never starts, so I move that read without touching checkout.
  • mongo Nearby, city, rating, and cuisines sit on one restaurant document. A SQL replica still fights geo and the card shape. Redis does not become the catalogue.
  • peak A replica set lets the list read a secondary. That is how we take lunch off the primary, not by adding Java threads.
  • later The same document is what Atlas Search and a country cluster will use. Picking Mongo only for year one would force a second store.
6–12 months

Short-term plan

what

Consumer list, nearby, and search run on a Mongo replica set. The partner portal still writes SQL.

why

Take the peak read off the monolith so a slow list stops costing orders this year.

how

Copy restaurant rows by the existing id. Dual-write is out: a partner save must not depend on Mongo being up.

when

Stream, replica set, shadow compare, then flip consumer reads. Done inside twelve months.

6–12 months

Sequence in that year

  • now Keep this API and this document. The Mongo _id is the Restaurant ID the portal already uses, so a retry cannot create a second place.
  • 1–3 m Stream from Gurugram SQL into Mongo. Stand up a replica set so the list can read a secondary. The single Docker node is only the demo.
  • 3–6 m Shadow a slice of list, nearby, and search against the old endpoint. Compare counts, ids, and distances, then flip consumer search.
  • 6–12 m Watch indexes and deep pages. Scale the database first. A cursor or a first-page cache only after we measure a hot path.

2–3 years

Long-term plan

what

Restaurants become source of record on Atlas. Then menus. Then orders. Payments stay with the current provider.

why

Cloud, more countries, and residency rules. A Gurugram SQL estate cannot be that store.

how

Same API, Atlas connection, then portal writes here and the SQL copy stops. countryCode picks the cluster.

when

Atlas after reads are stable. Write flip after Atlas. Next domain only after restaurants are done.

2–3 years

Cloud, residency, and security

  • india First Atlas cluster is India. Encryption at rest and backups come with it. Gurugram Mongo goes away.
  • residency countryCode routes to a cluster. Code 1 stays in India. A new country is a cluster and a routing rule, not a branch in the resource.
  • catalogue This collection is public restaurant data. Search coordinates are a query parameter and are never stored. Diner profiles never land here.
  • access Partner login stays on the portal. This API stays a catalogue on the platform network. I add keys only if it is exposed beyond that.

trade-offs

Calls I will defend

  • truth SQL is source of record in year one because a failed Mongo write must not roll back a partner save. After the write flip, Mongo is truth and the copy stops.
  • sync Copy from the SQL log and retry from the offset. Dual-write only if measured lag is itself losing the list — and then with an outbox.
  • peak Replica set and indexes first. I will not scale Java threads to hide a missing secondary, and I will not add a cache before we see a hot key.
  • cut No big-bang, no Atlas on day one, no orders in this slice. Discovery can lag. Checkout cannot.
close

What I am recommending

Peel restaurant search this year. Live next to SQL. Move the writer to Atlas when reads are stable, then repeat for menus and orders.
